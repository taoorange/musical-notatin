# 标注导出位置错乱问题排查与修复

## 1. 问题描述

在 `five-line-staff` 项目中，通过 OSMD 渲染引擎在页面上点击添加的乐器标注，导出到 MusicXML 后 `<direction>` 元素被插入到错误的小节（measure）。

**典型案例**：
- 截图中的 "TUBA" 标注实际屏幕位置在 "导播2"（measure number=9）之后
- 单击位置归一化坐标：`nx=0.66, ny=0.075`
- 导出的 XML 中，该标注的 `<direction>` 元素被插入到 `measure number="15"`（`fls:measureIndex0="14"`）
- 标注实际应该出现在 measure 9～10 附近

## 3. 根因分析（完整排查过程）

问题并非单一 bug，而是 **四个层层递进的缺陷** 叠加导致。以下按排查顺序逐一说明。

---

### 3.1 Bug 1：`Number(null) = 0` 陷阱

**位置**：`musicXmlNoteAnchors.ts` · `pickTimedNoteForAnnotationRecord()`

**现象**：标注被固定锚定到 measure[0]（导播1 的位置）。

**根因**：

```typescript
// 旧代码：Number(null) = 0，通过 Number.isFinite(0) 检查
if (Number.isFinite(ann.anchorMeasureListIndex0) && ann.anchorMeasureListIndex0 >= 0) {
  // 命中 measure[0]！
}
```

`resolveViewportAnnotationAnchorOnScoreXml()` 调用时传入 `anchorMeasureListIndex0: null`，但 `Number(null) === 0`，导致空锚点被当作指向 measure[0] 的有效索引。

**修复**：显式判空 `!= null`：

```typescript
const rawMi = ann.anchorMeasureListIndex0
if (rawMi != null && Number.isFinite(rawMi) && rawMi >= 0 && rawMi < measures.length) {
  // 安全
}
```

同样修复了 `anchorTickStart` 的判空。

---

### 3.2 Bug 2：OSMD 渲染硬编码 A4_P 页面格式

**位置**：`osmd.ts` · `renderMusicXmlWithOsmdPages()` + `HomePage.vue`

**现象**：OSMD 始终以 A4 竖版（210×297mm）渲染，而实际 MusicXML 页面为 A3（297×420mm），导致每页包含的 measure 数量与预期不符。

**根因**：

```typescript
// HomePage.vue 旧调用：
const osmdPaged = await renderMusicXmlWithOsmdPages(xmlForRender, {
  paged: true,
  // 未传 pageWidth/pageHeight → OSMD 内部默认 A4_P
})
```

当不传 `pageWidth`/`pageHeight`/`pageFormat` 时，`resolveOsmdPageFormat()` 回退到默认 `A4_P`，而目标 MusicXML 的 `<defaults>` 定义了 A3 尺寸（297×420mm）。页面格式不同 → OSMD 分页布局不同 → 每页 measure 分布不同 → 坐标映射错误。

**修复**：

1. 新增 `extractMusicXmlPageDimensionsInMm()` — 从 `<defaults>` 的 `<scaling>` + `<page-layout>` 计算实际 mm 尺寸
2. `renderMusicXmlWithOsmdPages()` 在调用方未显式指定格式时自动提取 MusicXML 页面尺寸
3. 移除 `HomePage.vue` 中 OSMD 调用处的硬编码 `pagedFormat: 'A4_P'`

```typescript
// osmd.ts 新逻辑：
const userSpecifiedFormat =
  typeof options.pageWidth === 'number' ||
  typeof options.pageHeight === 'number' ||
  typeof options.pageFormat === 'string'
const resolvedOptions = userSpecifiedFormat
  ? options
  : (() => {
      const dim = extractMusicXmlPageDimensionsInMm(musicXml)
      if (dim) return { ...options, pageWidth: dim.widthMm, pageHeight: dim.heightMm }
      return options
    })()
```

---

### 3.3 Bug 3：IndexedDB 缓存 key 不含页面尺寸

**位置**：`HomePage.vue` · `loadScoreFromOpenedFile()` + `osmd.ts`

**现象**：即使修复了 Bug 2，用户重新打开文件后，标注仍导出到 measure 14。控制台显示 bounds 未变。

**根因**：

```typescript
// 旧代码：OSMD 的 layoutVersion 硬编码，不随页面尺寸变化
layoutVersion =
  renderEngine.value === 'osmd'
    ? `${VEROVIO_LAYOUT_CACHE_VERSION}-osmd-paged-v3`  // ← 无页面尺寸信息
    : getVerovioLayoutVersion()
```

用户之前以 A4_P 渲染的 `osmdPageMeasureIndexBounds` 被 IndexedDB 缓存。即使修复了 Bug 2 让 OSMD 以 A3 重新渲染，如果缓存 key 不变，旧 bounds 会被直接复用。更糟的是，旧 A4_P 和 A3 渲染出来的页数恰好相同（都是 27 页），通过了 `ob.length === pages` 的验证。

**修复**：

1. 导出 `extractMusicXmlPageDimensionsInMm` 供 HomePage 使用
2. OSMD 模式下**提前读取文件**提取页面尺寸，写入 `layoutVersion`：

```typescript
// HomePage.vue 新逻辑：
if (renderEngine.value === 'osmd') {
  // 提前读文件 → 提取 <defaults> 页面尺寸
  earlyMusicXml = await file.text()
}

layoutVersion = renderEngine.value === 'osmd'
  ? (() => {
      const dims = earlyMusicXml ? extractMusicXmlPageDimensionsInMm(earlyMusicXml) : null
      const dimTag = dims ? `${dims.widthMm}x${dims.heightMm}` : 'default'
      return `${VEROVIO_LAYOUT_CACHE_VERSION}-osmd-paged-v3-${dimTag}`  // ← "2026-04-23-v2-osmd-paged-v3-297x420"
    })()
  : getVerovioLayoutVersion()
```

旧 key `...-osmd-paged-v3` 与新 key `...-osmd-paged-v3-297x420` 不匹配 → 旧缓存自动失效 → OSMD 以 A3 重新渲染 → 正确 bounds。

### 3.4 Bug 4（核心问题）：SVG BBox 与 OSMD measure 坐标单位不匹配 → 视口大小不兼容

**位置**：`osmd.ts` · `pageMeasureInkNormSpansFromOsmd()` + `musicXmlNoteAnchors.ts` · `pickTimedNoteForViewportPlacement()`

**现象**：修复 Bug 1～3 后，`fls:measureIndex0` 在正常窗口下变为正确的 measure 9（通过临时启发式检测绕过），但全屏模式下导出的 `measureIndex0` 变为 30 和 46——完全错误，且导出文件中缺少 `fls:dbgBounds` 属性。说明归一化结果在不同视口尺寸下不一致。

**根因**：

`pageMeasureInkNormSpansFromOsmd()` 中的归一化公式：

```typescript
// 旧代码：
const left  = (m.left  - inkX) / inkW
const right = (m.right - inkX) / inkW
```

其中：
- `m.left` / `m.right` 来自 `getPageMeasureHorizontalLayouts()` — **OSMD 内部 measure 坐标**（OSMD sheet units，与容器宽高成比例缩放）
- `inkX` / `inkW` 来自 `svg.getBBox()` — **SVG 用户坐标**（像素或 viewBox 单位，与 OSMD 内部坐标不在同一坐标系）

两者的比例关系不稳定：
- 正常窗口：BBox 宽度 ~2000px，measure 宽度约 200 OSMD units → 比例约 10:1 → span 被压缩到 [0, 0.08]
- 全屏窗口：BBox 宽度 ~8000px（容器 `max(innerWidth×2, 1800)` 增大），但如果有 viewBox，BBox 返回 viewBox 单位（不变） → 归一化结果"看似正常"，但点击位置 nx 是基于容器比例计算的，与 span 坐标存在偏移

临时修复（启发式检测 `spanRangeX < 0.3`）在正常窗口有效，但在全屏下失效（span 归一化"看似正常"，检测不触发，走 distance fallback → 选错 measure）。

**永久修复**：完全放弃 `svg.getBBox()`，改用 **measure 自身的 extent 做归一化**：

```typescript
// 新代码：使用 measure 自身的坐标范围归一化（viewport-independent）
const maxRight = Math.max(...measures.map((m) => m.right))
const minLeft = Math.min(...measures.map((m) => m.left))
const hRange = maxRight - minLeft || 1
// ...
const left  = (m.left  - minLeft) / hRange
const right = (m.right - minLeft) / hRange
```

垂直方向同理：

```typescript
// 用 measure 自身的垂直 extent 替代 BBox
let vMinTop = Infinity, vMaxBottom = -Infinity
for (const m of measures) {
  const ve = vertForPage.get(m.measureListIndex)
  if (ve) { vMinTop = Math.min(vMinTop, ve.top); vMaxBottom = Math.max(vMaxBottom, ve.bottom) }
}
const vRange = vMaxBottom - vMinTop || 1
// ...
let top    = clamp01((v.top    - vMinTop) / vRange)
let bottom = clamp01((v.bottom - vMinTop) / vRange)
```

**为什么 measure extent 归一化是 viewport-independent**：
- `m.left`、`minLeft`、`maxRight` 都来自 OSMD 同一内部坐标系（sheet units）
- 当容器大小变化时，所有这些值同比例缩放
- `(m.left - minLeft) / (maxRight - minLeft)` 在不同视口下得到相同的 [0,1] 归一化结果
- 同时移除了 `musicXmlNoteAnchors.ts` 中 `spanRangeX < 0.3` 的临时启发式检测代码

**修复文件**：
- `src/lib/osmd.ts:164-234` — 重写 `pageMeasureInkNormSpansFromOsmd()`，用 measure extent 替代 SVG BBox
- `src/lib/musicXmlNoteAnchors.ts:327-350` — 移除 `spanRangeX < 0.3` 启发式检测，恢复标准 distance fallback

## 5. 标注锚点选择完整链路

```
用户点击屏幕
  │
  ├─ ScorePinchViewport.onInnerClick()
  │   └─ clientToMusicNormXYInContainer(innerRef, clientX, clientY)
  │       → (nx, ny) in [0,1]
  │
  ├─ HomePage.onAddAnnotation()
  │   └─ resolveViewportAnnotationAnchorOnScoreXml(xml, {page, x, y}, ...)
  │       └─ pickTimedNoteForAnnotationRecord(ann, ...)
  │           ├─ 1. anchorMeasureListIndex0 ≠ null → stored-anchor 路径
  │           ├─ 2. anchorTickStart ≠ null → tick 匹配
  │           └─ 3. pickTimedNoteForViewportPlacement()
  │               ├─ in2d: nx/ny 同时落在 inkSpan 内
  │               ├─ inX:  nx 落在 inkSpan 内
  │               ├─ ⚠ distance fallback → ❌ Bug ④
  │               └─ miFallback (continuous) → ✓ 修复后使用
  │
  └─ 导出 MusicXML
      └─ insertFlsDirectionForAnnotation()
          ├─ 路径 A: anchorMeasureListIndex0 → 直接插入
          ├─ 路径 B: prePicked / anchorTickStart → 音符匹配
          └─ 路径 C: page → 回退估算
```

## 6. 验证方法

### 6.1 导出验证

1. 在 `five-line-staff` 中打开源 MusicXML 文件
2. 删除旧标注，重新在目标位置（导播2 后）点击创建 TUBA 标注
3. 导出 MusicXML
4. 检查导出文件中 `<direction>` 标签的 `fls:measureIndex0` 属性：
   - 应在 8～10 范围内（对应 measure number 9～11，接近导播2）
   - **不应为 0 或 14**

### 6.2 控制台验证

浏览器控制台应显示：
```
[pickTimedNoteForViewport] ⚠ inkSpan 归一化异常 (range=0.090, nx=0.659 在 [-0.010,0.080] 外)，跳过 distance fallback, 走 miFallback=9
```

### 6.3 回归测试

修复后应验证以下场景不受影响：
- 有 `anchorMeasureListIndex0` 的标注 → 使用 stored-anchor 路径
- 仅有 `anchorTickStart` 的标注 → 使用 tick 匹配
- 仅靠 page/x/y 的旧标注 → 回退到 miFallback（如遇归一化异常自动跳过 distance fallback）
- 同小节多个标注 → `spreadTimedNotePickForExport` 正常扩散
